# Codex 直接用还是接进智能体框架？两种用法的区别

> 2026-11-23 · 历元技术笔记 · 约 7 分钟阅读

用 Codex 写代码，常见的有两种方式：一种是在电脑上直接用，另一种是接进 Hermes Agent 这类智能体框架，让框架去调用它。这篇笔记里我们比较这两种用法，说明各自适合哪些场景、要做哪些权衡，最后给出我们采用的混合工作流。

先说结论：两者的核心区别不在 Codex 本身的能力，而在于**谁来组织任务、什么时候运行、能访问什么环境**。不管用哪种方式，Codex 模型都运行在 OpenAI 云端，接进智能体框架并不会让它变成本地模型。

## 一、直接在电脑上使用 Codex

这里说的“直接用”，是指 Codex 桌面端、IDE 插件或 Codex CLI。

**优势：**

- 可以直接访问本机的项目、Git 仓库和开发环境；
- 交互链路短，响应快，出故障的环节少；
- diff、终端输出可以实时看到，执行命令前也能逐条审批；
- 能用上 Codex 自带的沙箱、插件、worktree 和代码审查功能；
- 适合连续编码、调试、UI 开发这类需要人频繁介入的任务。

**不足：**

- 基本上要人主动打开才会工作；
- 没有跨项目的长期记忆，也不了解业务上下文；
- 远程控制、定时任务、跨工具编排都不是它的强项；
- 电脑休眠或关机后，后台任务就停了；
- 需求要自己描述，过程要自己检查，多个任务也要自己管理。

**适合场景：** 人坐在电脑前开发、调试、审查代码。

## 二、在智能体框架中使用 Codex

以 Hermes Agent 为例，接入方式有两种。

### 方式 A：框架调用 Codex CLI 完成编码任务

调用链路是：用户 → Hermes → Codex CLI → 项目代码。

Hermes 负责理解需求、准备工作目录或 Git worktree、调用 Codex、监控长任务、收集结果、运行测试，最后通过消息渠道（比如 Telegram）汇报。Codex 只管具体的编码。

要注意，这种方式下 Hermes 自己用的模型也要消耗额度，Codex 另外消耗它自己的使用额度，两份是分开算的。

### 方式 B：Codex 作为框架的主运行时

Hermes 也可以把整段对话交给 Codex app-server 处理，两者分工如下：

| 角色 | 负责范围 |
| --- | --- |
| Codex | 推理、终端操作、修改文件、沙箱 |
| Hermes | 会话管理、消息渠道、记忆、技能、浏览器及其他外围工具 |

这种方式可以直接用 ChatGPT 账号的 Codex OAuth 登录，一般不需要另配 OpenAI API Key。

不过在 Codex 运行时下，Hermes 的部分原生能力会受限，主要是在对话中途调用的那些：持久记忆工具、跨会话搜索、普通子 Agent 委派、Hermes 自带的 Todo 工具。其中一部分能力在会话开始时、外围流程里，或者切回 Hermes 默认运行时之后仍然能用。

## 三、六个维度的实际差异

### 1. 编程能力

账号、模型和代码上下文都相同时，两种方式的核心编程能力基本一样。智能体框架不会让 Codex 写代码更聪明，它带来的是这几样东西：编排、自动化、长期上下文、远程入口、多工具联动。

### 2. 使用额度

如果框架是通过同一个 ChatGPT 账号的 OAuth 调用 Codex：

- 本机的 Codex 和框架里的 Codex 一般共用同一份账户额度；
- 接进框架并不会多出一份 Codex 额度；
- 两边同时跑，这份额度会用得更快；
- 一旦触到 Codex 的使用上限，两边可能都会受影响。

如果框架外围还用 Claude、Gemini 等其他模型做规划，这部分费用或额度另外计算。另外，订阅提供的是一份有上限的使用额度，不是无限使用。桌面端、IDE、CLI 和框架登录同一个账号时，通常都从这一份里扣。

### 3. 文件访问范围

| 使用方式 | 可访问范围 |
| --- | --- |
| 本机直接使用 | 本机项目和软件环境 |
| 框架部署在云服务器 | 默认只能访问服务器上的文件，访问不到本机文件 |

- 要让框架改本机上的项目，得先把仓库同步到服务器，或者通过 SSH、Git、节点连接打通；
- 同一个仓库，不要让本机 Codex 和框架同时直接改同一个工作目录，很容易冲突。应该各用独立分支或 worktree。

### 4. 自动化能力

本机直接用的 Codex 更像一个即用即走的开发工具。智能体框架更适合下面这些事：

- 从消息渠道发一句话就启动任务；
- 定时运行；
- 管理多个项目；
- 自动为任务创建独立 worktree；
- 写完代码自动跑测试；
- 失败时发通知；
- 生成看板、文件、报告；
- 串联浏览器、搜索、数据库和消息渠道。

### 5. 安全性

本机直接使用更方便监督：每条命令都看得到，权限范围清楚，出了问题能马上中断。

框架在无人值守时运行，风险更高，需要做好这些防护：

- 固定工作目录；
- 用 Git 分支或 worktree 做隔离；
- 限制可写路径；
- 保留 Codex 沙箱；
- 默认不使用高风险的全权限模式；
- 对外发送、部署、删除、数据库迁移之前必须审批；
- 不让消息渠道或其他用户接触到 Codex 的 OAuth 凭据文件。

还有一点要特别注意：在 Gateway 或服务进程中调用 Codex 时，workspace-write 沙箱可能因为 Linux 用户命名空间的限制而启动失败。碰到这种情况，不应该图省事长期关掉沙箱，而是要修好运行环境，或者在外面再加一层隔离。

### 6. 稳定性与速度

| 使用方式 | 特点 |
| --- | --- |
| 本机直接使用 | 链路短、交互快、排查问题简单 |
| 框架中使用 | 多了一层编排，上下文和工具调用更多，可能更慢、消耗也更多；但适合长时间后台运行和无人值守的任务 |

## 四、我们采用的混合模式

我们觉得这两种用法不必二选一，按任务类型分工就行。

**本机 Codex 负责：**

- 开发新功能；
- 调试工作流和插件；
- 调整前端页面的视觉效果；
- 需要频繁查看结果的工作；
- 大规模重构、复杂 Bug 排查；
- 提交前的人工审查。

**框架中的 Codex 负责：**

- 接收远程下发的开发任务；
- 定时巡检业务系统；
- 自动修复边界清楚的小问题；
- 批量处理数据；
- 后台跑测试和代码审查；
- 调度多个仓库、多个任务；
- 任务完成后推送结果。

**协作流程：**

1. 框架接收需求，整理成任务说明；
2. 为这个任务创建独立的 Git worktree；
3. Codex 在 worktree 里开发、测试；
4. 框架汇总 diff、测试结果和风险点；
5. 开发者在本机审核；
6. 审核通过后再合并、部署。

## 小结

- 如果只是写代码，在本机直接用 Codex 更简单、更快，也更好控制。
- 如果需要远程控制、记住业务规则、定时运行和跨工具自动化，接进智能体框架会更强，但复杂度和安全风险也随之上升。
- 两种方式背后是同一个云端模型，额度通常也是同一份。框架带来的是编排和自动化，编程能力本身不会变强。

我们比较认可这样的定位：本机 Codex 做主力开发台，智能体框架做远程的项目管理和自动化调度层，Codex 作为框架调用的编码执行器。无人值守的部分一定要配好隔离和审批。
